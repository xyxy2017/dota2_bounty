# Dota 2 历史相遇玩家标记工具 PRD

## 1. 文档信息
- 产品名称：Dota 2 历史相遇玩家标记工具
- 文档版本：v0.2
- 文档日期：2026-04-29
- 文档类型：通用 PRD
- 当前阶段：MVP 定义
- 产品形态：本地后台小进程，暂不提供前端

## 2. 项目背景
在 Dota 2 对局中，玩家会反复匹配到曾经交手过的人，但通常无法在短时间内回忆起对方上一次使用的英雄、双方当时是队友还是对手、最终输赢结果，以及自己对该玩家的主观印象。

现有 Dota 2 工具大多偏向战绩、选人和统计分析，缺少一个围绕“再次相遇提醒”和“历史恩怨记忆”设计的轻量产品。同时，Overwolf 这类平台接入成本较高，部分用户不愿意为了单一需求额外安装重平台。

因此，本项目优先采用`本地小进程`方式实现，先验证数据采集与历史命中的核心闭环，暂不投入前端展示。

## 3. 产品愿景
构建一个轻量、低打扰、可长期积累数据的 Dota 2 本地伴随工具，在用户再次匹配到历史玩家时，自动提醒上一次同局信息，帮助用户快速恢复记忆并辅助决策。

一句话定义：

`一个本地运行的 Dota 2 历史相遇玩家记录与提醒工具，自动记录你匹配过的玩家，并在再次遇到时提示上次同局的英雄、敌友关系、输赢结果和个人备注。`

## 4. 产品目标

### 4.1 业务目标
- 验证“再次匹配历史玩家提醒”这一需求是否成立
- 以极低前置成本完成从记录到再提醒的最小闭环
- 为后续加入前端展示、标签管理和更复杂分析建立数据基础

### 4.2 用户目标
- 不再忘记曾经匹配过的重要玩家
- 在再次相遇时快速知道对方上次玩的英雄和对局结果
- 能逐步积累个人化的“路人关系数据库”

### 4.3 MVP 目标
- 本地自动记录玩家相遇历史
- 在后续对局中自动识别历史玩家
- 在无完整前端的前提下完成最小提醒闭环
- 通过日志、状态文件或本地事件输出验证功能成立

## 5. 目标用户

### 5.1 核心用户
- 经常单排或双排的 Dota 2 玩家
- 在意“这个人我以前见过吗”的玩家
- 会对某些路人形成明显主观印象的玩家

### 5.2 典型用户特征
- 局数较多，重复遇人概率高
- 愿意安装轻量本地工具，但不愿为了单一功能下载重平台
- 对个人化标记、备注、恩怨记录有明确需求

## 6. 用户痛点
- 再次匹配到某个玩家时，无法快速回忆上次同局情况
- 对“仇人”“毒瘤”“靠谱队友”等关键对象缺少长期记忆工具
- 通用战绩产品信息量大，但缺少“我和这个人之间发生过什么”的视角
- 游戏过程中没有足够时间手动查询历史数据

## 7. 核心场景

### 7.1 主场景
用户完成一场对局后，系统自动记录该局所有相关玩家与结果；在未来某一局再次匹配到其中某人时，系统自动命中历史记录并给出轻量提醒。

### 7.2 典型场景
- 场景 A：用户再次匹配到上次的对线对手，希望立刻知道对方上次玩的英雄和那局输赢
- 场景 B：用户再次匹配到曾经很靠谱的队友，希望在游戏开始前快速认出对方
- 场景 C：用户想在赛后回查某个玩家过往交手记录，决定是否给出标签

## 8. 用户故事
- 作为一名高频单排玩家，我希望系统自动记录我遇到过的玩家，这样我不需要手动整理名单
- 作为一名会记仇的玩家，我希望再次遇到某个玩家时能看到上次他的英雄和输赢结果，这样我能快速回忆上一局发生了什么
- 作为一名希望识别靠谱队友的玩家，我希望保留自己的备注和标签，这样下次遇到时我能更快建立判断
- 作为一名轻量工具用户，我希望产品可以后台运行，不要求我额外打开复杂界面

## 9. 产品范围

### 9.1 本期范围
- 本地小进程常驻或手动启动
- 自动采集和记录历史玩家相遇数据
- 基于本地数据库进行历史玩家命中
- 提供最小提醒输出
- 提供基础标签和备注数据结构
- 暂不开发完整前端页面

### 9.2 不在本期范围
- 不接入 Overwolf
- 不开发完整图形前端管理界面
- 不做账号体系和云同步
- 不做复杂统计分析和推荐
- 不做跨设备数据同步
- 不做社交分享、排行榜、社区能力
- 不采用注入式、侵入式、高封禁风险的数据获取方式

## 10. MVP 定义

### 10.1 MVP 核心闭环
1. 系统在对局过程中或赛后拿到本局玩家和比赛结果
2. 系统把相关玩家和本局关系数据写入本地数据库
3. 系统在后续对局中识别出历史玩家
4. 系统输出最小提醒信息

### 10.2 MVP 必备功能

#### F1：本地后台进程
- 支持本地启动、停止和运行状态检测
- 支持日志输出
- 支持本地配置文件
- 支持单实例运行，避免重复采集

#### F2：对局数据采集
- 获取本局中出现的玩家唯一标识
- 获取玩家昵称
- 获取双方英雄信息
- 获取敌友关系
- 获取对局完成时间和结果
- 获取 `match_id` 或等价唯一对局标识

#### F3：历史数据落库
- 自动保存本局相遇记录
- 对玩家维度做去重和更新
- 保留最近一次昵称
- 记录首次遇见时间与最近一次遇见时间

#### F4：历史玩家命中
- 在后续对局中识别当前局玩家是否出现在历史数据库中
- 支持按玩家唯一标识匹配
- 支持提取最近一次相遇记录
- 支持统计历史相遇次数

#### F5：最小提醒输出
- 在识别到命中时输出提醒事件
- 提醒内容至少包含：
  - 玩家昵称
  - 上次相遇时间
  - 上次是队友还是对手
  - 对方上次英雄
  - 我方上次英雄
  - 输赢结果
  - 标签和备注

#### F6：标签与备注数据支持
- 支持为玩家保存标签字段
- 支持为玩家保存文本备注
- MVP 阶段允许通过配置文件、命令行或直接操作本地数据方式维护

## 11. MVP 非目标
- 不追求完整的游戏内可视化体验
- 不解决所有战绩分析需求
- 不在第一版引入复杂筛选、排序和搜索页面
- 不在第一版实现智能推荐和自动分类
- 不把托盘、悬浮窗、管理页作为立项前提

## 12. 系统边界

### 12.1 系统负责
- 采集与当前玩家相关的对局数据
- 在本地建立“历史相遇玩家”索引
- 在再次识别到同一玩家时生成命中事件
- 将命中结果写入本地日志或消息通道，供未来 UI/通知模块消费

### 12.2 系统不负责
- 游戏内展示
- 跨设备同步
- 社交分享
- 大规模公共战绩查询平台能力

## 13. 核心数据链路假设
- 本地进程需要获得三类基础信息：
  - 当前账号标识
  - 当前或最近一局比赛的玩家名单
  - 对局完成后的英雄、队伍关系与胜负结果
- 数据链路分成两段：
  - 实时识别链路：在对局开始前后或可识别阶段获取本局玩家列表，用于判断是否命中历史玩家
  - 赛后补全链路：在比赛结束后获取完整对局明细，用于落库英雄、输赢、敌友关系
- MVP 可接受实时识别与赛后补全存在时间差
- 数据可信主键必须是 `steam_id / account_id` 一类稳定 ID，不能依赖昵称
- 如果实时阶段无法稳定拿到完整信息，系统允许先记录待补全数据，后续轮询赛果或明细补写

## 14. 功能需求明细

### 14.1 玩家记录
- 必须使用稳定唯一标识作为玩家主键
- 必须支持同一玩家多次相遇记录
- 必须能区分同一玩家在不同局中的英雄与输赢

### 14.2 相遇关系
- 必须记录用户与该玩家当时是队友还是对手
- 必须记录该局对用户而言的最终结果

### 14.3 备注能力
- 备注和标签为用户个人私有数据
- 标签建议预留枚举值：
  - 仇人
  - 毒瘤
  - 靠谱队友
  - 绝活哥
  - 关注

### 14.4 提醒策略
- 默认只对命中的历史玩家提醒
- 可预留未来配置项：
  - 仅提醒有标签的人
  - 每局最多提醒人数
  - 是否重复提醒同一玩家

## 15. 进程与模块设计

### 15.1 模块拆分
- `process supervisor`
- `game state watcher`
- `roster collector`
- `history matcher`
- `match resolver`
- `storage`
- `event bus`
- `logger`

### 15.2 模块职责
- 进程管理模块：负责常驻、单实例控制、生命周期管理、异常恢复
- 游戏状态探测模块：识别 Dota 2 是否启动及当前状态切换
- 对局玩家采集模块：在合适时机采集 roster，并做本地去重和标准化
- 历史命中模块：基于稳定 ID 查询本地库并生成命中结果
- 赛后结果补全模块：补全英雄、关系、输赢和时间等字段
- 标签与备注存储模块：保留用户私有标记能力
- 本地事件输出模块：把关键事件输出到日志、状态文件或事件表

### 15.3 运行流程
1. 进程启动
2. 初始化本地库与配置
3. 轮询游戏状态
4. 发现进入比赛上下文后启动本局采集
5. 采集 roster 并触发历史命中
6. 比赛结束后补全赛果
7. 持久化玩家与 encounter
8. 输出事件并回到待机状态

## 17. 事件输出与可观测性

### 17.1 关键事件
- `match_detected`
- `roster_collected`
- `historical_player_hit`
- `match_result_resolved`
- `encounter_persisted`
- `retry_failed`

### 17.2 输出形式
- 本地日志文件
- SQLite 事件表
- 简单本地 socket / named pipe 预留接口

### 17.3 日志要求
- 必须有结构化日志
- 至少包含：时间、事件类型、`match_id`、`steam_id`、阶段状态、结果码
- 对采集和落库都要记录成功/失败原因
- 缺失字段要明确标记为 `unknown`、`pending` 或 `partial`
- 日志按日期切分，便于长期运行排查

## 18. 非功能需求

### 18.1 轻量性
- 后台进程常驻时资源占用应尽量小
- 不依赖额外重平台运行
- 安装包应保持轻量

### 18.2 稳定性
- 采集失败时不应影响用户正常游戏
- 程序异常退出后应支持恢复运行
- 数据库写入失败时需要日志可追踪

### 18.3 隐私性
- 所有数据默认本地存储
- MVP 不上传用户数据到云端
- 应明确标识本地记录范围

### 18.4 可扩展性
- 为后续图形前端接入保留数据层接口
- 为后续统计页和搜索页预留字段

## 19. 关键假设与技术前提
- 可以通过本地小进程以合规方式获取 Dota 2 对局中的必要玩家和结果数据
- 玩家唯一标识可稳定获取并用于跨局关联
- 赛后结果和英雄数据可在可接受延迟内补齐
- 用户愿意通过轻量方式维护少量备注和标签
- MVP 的首要目标不是“展示”，而是“建立可持续、可追溯、可命中的本地玩家历史数据库”

## 20. 关键风险与应对

### 20.1 数据源风险
风险：
无法稳定拿到对局内玩家列表、英雄或结果数据。

应对：
- 在开发前先完成数据采集 POC
- 把“拿到玩家唯一标识、英雄、输赢结果”设为立项门槛

### 20.2 识别时机风险
风险：
无法在足够早的阶段识别当前局玩家，影响提醒价值。

应对：
- MVP 先接受“在可识别时机提醒”，不承诺必须在最早阶段出现
- 后续再优化识别时机

### 20.3 无前端带来的可用性风险
风险：
用户无法方便维护标签和备注。

应对：
- MVP 先只验证记录与识别闭环
- 标签维护先走配置文件或简单命令方式
- 下一阶段再加入最小桌面管理页

### 20.4 合规风险
风险：
数据采集方式可能触碰平台或游戏限制。

应对：
- 仅采用合规的数据获取方式
- 在方案设计阶段明确禁止侵入式实现

### 20.5 数据质量风险
风险：
实时识别和赛后补全来自不同来源，字段可能缺失或冲突。

应对：
- 统一 provider 抽象
- 支持 `pending / partial / failed` 状态
- 允许延迟补全，不阻断主流程

## 21. 成功指标

### 21.1 MVP 成功标准
- 系统可稳定记录至少 1 场完整对局的玩家相遇数据
- 系统可在后续对局中成功命中历史玩家
- 命中后可输出完整最小提醒信息
- 不依赖前端页面完成闭环

### 21.2 质量指标
- 单局数据丢失率低
- 多次相遇记录可正确归属到同一玩家
- 后台常驻不明显影响游戏体验
- 数据源失败时不会导致主进程崩溃

### 21.3 后续可跟踪指标
- 每周记录的对局数
- 每周命中的历史玩家数
- 用户新增标签数
- 有标签玩家的复遇命中率

## 22. 测试与验收标准

### 22.1 核心验收项
- 启动后台进程后，程序可正常运行并持续输出状态日志
- 完成一局对局后，本地数据库中能看到新增记录
- 同一玩家二次相遇时，系统能正确命中该玩家
- 命中输出包含最近一次相遇的核心信息
- 标签和备注字段不会因新数据写入被覆盖丢失

### 22.2 异常验收项
- 采集异常时程序不会崩溃
- 数据缺失时可回退为部分提醒
- 重启程序后数据库数据仍可正常读取
- 数据库锁定、网络不可用、文件损坏时有明确失败标记

### 22.3 关键测试场景
- 首次运行场景：本地库为空，启动后可正常初始化
- 单局记录场景：完整打一局后，能正确记录玩家和结果
- 重复相遇场景：再次遇到同一玩家时，能正确命中
- 昵称变化场景：昵称变化后仍能通过稳定 ID 关联
- 多玩家命中场景：同一局命中多个历史玩家时，可分别输出对应记录
- 断线重连场景：记录不重复、不丢失
- 异常退出场景：进程被杀死后，重启可恢复状态
- 数据冲突场景：同一局重复上报时，能去重
- 无网络场景：外部数据不可用时，仍可保存本地最小字段集
- 高负载场景：连续多局快速切换时资源占用可接受

## 23. 失败处理要求
- 采集失败时，不中断进程，只记录错误并进入下一轮轮询
- 数据库写入失败时，先缓存到本地待重试队列
- 外部数据源不可用时，允许先保存最小字段集，后续补全
- 识别到重复事件时，必须幂等处理
- 遇到权限不足、文件损坏、数据库锁定时，要给出明确错误码和恢复建议
- 进程异常重启后，应能继续读取上次状态

## 25. 多 Agent 推进分工

### 25.1 审阅与分配 Agent
负责：
- 明确项目边界
- 审阅需求是否偏离“轻量本地小进程 MVP”
- 识别主要风险
- 给产品、开发、测试角色分配任务

输出物：
- 范围定义
- 风险清单
- 里程碑建议

### 25.2 产品 Agent
负责：
- 用户问题定义
- 用户故事和使用场景
- MVP 范围与非目标
- 成功指标和路线图

输出物：
- PRD 主文档主体
- 功能优先级说明

### 25.3 开发 Agent
负责：
- 梳理数据采集链路和系统边界
- 明确本地进程、存储和模块拆分
- 定义 MVP 可交付里程碑

输出物：
- 技术约束说明
- 模块分解
- 开发里程碑

### 25.4 测试 Agent
负责：
- 定义验收标准
- 设计核心链路测试点
- 补充异常场景与回归关注点

输出物：
- 测试清单
- 验收标准
- 风险回归建议

## 26. 后续建议
- 下一步优先产出技术方案文档，而不是继续细化前端交互
- 第一里程碑应以“数据采集 POC 成功”为唯一门槛
- 若 POC 无法稳定获取关键字段，应及时收缩目标或调整技术路径
- 在 POC 跑通前，不建议投入托盘、悬浮窗或前端管理页开发
